## 2. A 类详情

### A1 · 形态一会话未绑定主体

- **问题**：`POST /messages?sessionId=X` 只按 `sessionId` 路由，**不校验请求者是否该会话的主人**；而 `sessionId` 在 **URL** 里 → 必然进访问日志 / APM / 报错页（**M13 自己就要求对它脱敏**，等于承认它会漏）。
- **危害**：JSON-RPC 的 `id` 由客户端自编且通常是**小整数** → 攻击者用**自己合法的 Token** 把响应写进受害者流，只要 `id` 撞上其在途请求，客户端就**把伪造的工具输出当成自己那次调用的结果交给模型** = **对另一个租户 agent 的提示词注入**。
- **边界（不夸大）**：按本决策实现后攻击者**读不到**受害者响应、也**调不到**自己无权调的工具 → 属**完整性 / 越权写入**；但若实现者图省事写成"**会话即身份**"（`GET /sse` 已鉴权，POST 复用会话身份），立即升级为**跨租户冒充 + 读取**。规范写 MUST NOT 就是为这个。
- **决策**：① `GET /sse` 记录 `{tenantId, userId, tokenId}`，每次 POST 校验主体一致；② 不一致 → **拒绝写入流** + 对外统一 **`404`**（不区分"不存在"与"不属于你"）；③ **默认不终止会话**；④ 任何路径不得回退到"会话即身份"。
- **为什么不是 `401`**：`401` = 未通过认证。此处攻击者 Token **有效、认证已成功** → 回 `401` 会让客户端误以为该刷新 Token，而它重试同一 `sessionId` **永远不会成功**。`403` 语义正确但**泄漏会话存在性** → 取 `404`。
- **为什么"不终止会话"是修正**：原建议"检测到不匹配就终止会话"实为**送攻击者一个 DoS 开关**（拿到 `sessionId` 就能反复打死受害者会话）。
- **验收**：两个不同 Token + 一条 SSE 流 → 第二个 Token 的 `POST` 得 **`404`**，且**该流里一条消息都不多出来**。

### A2 · 阶段 0 免鉴权降级

- **问题**：阶段 0 只做 30 个核心接口（**不含登录**）＋ **A13** 要求"除 login 外都要带凭据（Bearer / cookie）"＋ 数据库稿 §3.4 写「都取不到 → **默认租户**」→ **照字面实现 = 未认证请求落默认租户直接放行**。
- **决策**：阶段 0 **明确免鉴权**（显式开关 `auth.mode = dev | jwt`），固定注入默认租户（`id=1`）+ 固定 dev 用户（`ROOT`）。
- **四道护栏（缺一不可）**：
  1. **显式开关 ≠ 降级兜底** —— 开关决定的是**固定值**；"任何取不到就降级"是**兜底**。**「管理面永不因缺 JWT 降级」结论不变**；
  2. **`spring.profiles.active=prod` + `auth.mode=dev` → 启动直接失败**（不是 WARN）；
  3. **现在就留 `AuthFilter` 骨架**，阶段 1 只换 `jwt` 分支实现，**不改 30 个 controller**；
  4. ✅ **`jwt` 模式下"不只验签，还要验人"**（2026-10-16 加，见 §5 **#18**）—— 除签名 + `exp` 外，**校验 `mcp_user.status = ACTIVE` 且未被删除**，配 **60 秒短缓存** ⇒ 停用/删除 **≤60 秒内生效**。
- **配套**：阶段 0 **不可对外部署** → 写进用户手册「限制」章节；✅ **`AuthFilter` 取 JWT 的来源 = 优先 `Cookie`、兼容 `Authorization: Bearer`**（2026-10-16，同源 cookie 方案的必要补充）。
- **验收**：① `prod` + `dev` 组合 → **启动失败**；② `jwt` 模式无 Token 请求 → **`401`**（不是落默认租户）；③ **禁用/删除用户 → ≤60 秒内 `40100`**。

### A3 · `url → blob` 的 SSRF

- **问题**：URL 来自**模型**（不可信输入）。原设计只有 5 条要点、**零验收用例**。
- **决策（8 条要求，每条可二值判定）**：协议白名单 `http`/`https`｜**默认不跟随重定向**（需跳转则管理员显式开、每跳全量校验、≤3 跳）｜**DNS 重解析校验 + 用解析出的 IP 直连**（防 TOCTOU / rebinding）｜地址黑名单（环回 / 私网 / 链路本地 / IPv6 本地 + **云元数据** `169.254.169.254`、`100.100.100.200`、`metadata.google.internal`）｜端口限制（env `SSRF_ALLOWED_PORTS`）｜连接 3s / 总 10s + 响应大小上限 + **流式丢弃不落盘**｜按 Token 频次限制 + 审计日志｜可选域名白名单。
- **决策**：**本条加强了原设计的默认行为** —— 原文写"限制重定向 ≤3 跳"，改为"**默认不跟随**"（默认关 = 默认安全），已经主人确认。
- **验收（8 条用例全部必须被拒）**：`http://localhost`｜`http://127.0.0.1`｜`http://169.254.169.254/latest/meta-data/`｜解析到 `10.x` 的内网域名｜302 跳 `127.0.0.1`｜**首次解析公网 / 二次解析 `127.0.0.1`**｜返回 5GB（`isError: true`，**不截断**）｜`file:///etc/passwd`。
- **备选（已评估、未采用）**：本期只保留 `base64 → blob` → SSRF 面**直接归零**。

### A4 · 敏感值清单与掩码

- **判定规则**：**这个值泄露后，攻击者能不能直接拿去访问上游、或冒充身份？** 能 → 敏感。→ URL / 名称 / 描述 / 开关**不是**敏感；**凭据与密钥是**。
- **敏感值全集（7 处落点）**：`mcp_service_auth_param.value`｜工具 `request_json` 里 header / cookie / query 的**值**｜`mcp_config` 中标 `isSecret` 的项｜`mcp_user.password_hash`（**不返回**，不是掩码）｜`mcp_client_token` 明文（**只出现一次**）｜`mcp_operation_log.detail_json`（**写入侧就过滤**）｜将来租户 SSO `client_secret`。
- **读写语义**：读 → `***`；写回 `***` = **保留原值**。
- **审批人也不给明文** —— 审批人的职责是判断"改动合不合理"，不是保管密钥；要验证 token 用**「测试」按钮真实发一次请求**更可靠。前端差异展示只给"已修改 / 未修改 / 已清空"三态。
- **修正说明**：原建议"给 `mcp_config` 加 `is_secret` **列**"**未采纳** —— `config_key` 必须来自 §12 枚举白名单，落列会与白名单**双源漂移**；改为标记记在白名单定义里。且按 §12.1 分层，**密钥类全在 env-only、不经 API**，所以**当前 6 个键全部非密钥**（不滥用掩码）。
- **验收**：① `sensitive=1` 的字段读回 `***`；② 写回 `***` → 值不变；③ 审批详情里**任何角色**都看不到明文。

### A5 · 密码哈希宽度与策略

- **问题**：`VARCHAR(100)` **装不下** Argon2id 编码串（本就偏短）；且全文档**无密码策略、无失败锁定**。
- **决策**：算法 **BCrypt cost 12**；列宽 **`VARCHAR(255)`**；策略 **≥8 位且含字母与数字**；**连续 5 次失败锁 15 分钟**；`mcp_user` 加 **`failed_attempts`** / **`locked_until`** 两列。
- **决策**：锁定与密码错误**必须给不同错误码** → 新增 **`42301`**（HTTP 423 Locked），**不得复用 `40100`**（否则前端分不清"密码输错"和"请稍后再试"）。
- **验收**：① 连续 5 次错误 → 第 6 次即使**密码正确**也回 **`42301`**；② 15 分钟后可用正确密码登录成功；③ 成功登录后 `failed_attempts` 归零。
- ✅ **已定（2026-10-16）**：「管理员重置密码后强制改密」**要** `must_change_password` 列（见 §5 **#1**，已关闭）。

### A6 · api-key 唯一性与物理隔离的结构性冲突

- **问题根因**（不只是"唯一索引没带 `tenant_id`"）：鉴权链是 `api-key → user → tenant`，**查 token 时还不知道租户** → 本质上要求一张**跨租户全局索引**，与 §3.3 约束 2（禁跨租户唯一键）**结构性冲突**；逃生舱（`SCHEMA` / `DATASOURCE` / `TABLE_PREFIX`）打开后 `uk_token_hash(token_hash)` 直接失效。
- **决策**：**明文 token 内嵌租户标识** → 鉴权先定位租户、再查该租户的表 → **全局唯一索引彻底取消**（改 `uk_token (tenant_id, token_hash, deleted_seq)` + 非唯一 `idx_token_hash`）。
- **格式**：
  ```text
  明文 token : mcp_<租户id 的 base36>_<base62(SecureRandom 32 字节)>
  库里        : token_hash = SHA-256(明文)
  展示        : token_prefix = mcp_<租户id base36>_7f3a
  主键        : 雪花（照 C2 不变）
  ```
- **为什么熵不能用雪花数**（主人的原提案）：雪花 = 41 位时间戳 + 10 位 workerId + 12 位序列，**高度可枚举**（知道大致创建时间，单 worker 一天内仅约 400 万候选），且雪花 id 到处出现在 URL 里不保密；**哈希不产生熵** —— `hash(tenantCode + 雪花)` 的熵就等于两者的熵。→ 保留内嵌租户标识的**收益**，把熵源换成 `SecureRandom`（JDK 自带，**不需要造数、不需要分配器**，满足"不新增编号体系"的原意）。
- **为什么内嵌雪花租户 id 而非 `tenantCode`**：`tenantCode` 有 `uk_tenant_code`、**允许改名** → 内嵌它会导致"改一次 code，该租户全部 token 失效"。
- **代价（认下）**：token 明文暴露租户 id —— 可接受（雪花 id 不保密、`tenantCode` 本就出现在登录参数里）。
- **验收**：① 库中**不存在** `token_hash` 上的全局唯一索引；② 鉴权**能仅凭前缀**定位租户；③ 两个租户各自签发 token 互不干扰。

| **有** | `0` | 应置 `0` | **完全不出现在 `inputSchema`** |

**三条硬规则**：**① `nonEmpty` 仅对 `string`/`string[]` 生效**；**② 有 `value` ⇒ `required` 失效**（UI 必须置灰）；**③ 未开 `overridable` ⇒ 该参数不进 `inputSchema`**（**这才是"凭据不暴露给模型"的唯一正确表达**）。

**「和/或」与必填的关系**：`AND` = 全组都要有值；`OR` = 至少一个有值 → **逐行 `required` 在 `OR` 组里语义不成立**，UI 必须按组关系约束。
