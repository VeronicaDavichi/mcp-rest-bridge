# 数据库设计（多租户版）

> 覆盖：**多租户**底座（租户 / 用户 / 权限）+ 控制台业务表（服务 / 工具 / 标签 / 导入）+ 审批流 + 通知 + 分层配置 + MCP 运行时表（api-key、可见范围、日志、产物、可选会话与协商版本缓存）。
> 目标：**同一套 DDL 语义在 MySQL 8.0 与 PostgreSQL 14+ 上都能跑**，且唯一性 / 软删除 / 排序 / 租户隔离的语义两库完全一致（见 [`数据库兼容性评估.md`](./数据库兼容性评估.md)）。
> 隔离策略：**共享库共享表 + `tenant_id`**，但**依赖层预留物理表隔离的逃生舱**（第 3 章）。
> 状态：**v0.2 多租户版**。⚠️ 其中**9 条是我按推荐值替你定的**，集中列在**第 19 章**，任一条不顺眼直接说。

## 1. 目标、边界与不做什么

**做**：多租户行级隔离的完整表结构、角色与权限模型、审批流（草稿式）、通知、分层配置、索引、迁移组织、级联策略、数据字典、验收标准。

**不做（本期）**：

1. **不做物理隔离的落地实现**（只留逃生舱：4 种模式 + 5 条必须守住的约束，见 3.2 / 3.3）；
2. **不做用户组**（只留权限判定抽象点 `PermissionService.can()`，见 4.4）；
3. **不做 api-key 审批流**（你的定案：**点一下就生成**）；
4. **不做分库分表 / 分区**；日志靠时间索引 + 应用层归档；
5. **不建物理外键**；
6. **不建"无功能设计"的表**：`资源` / `提示词`（M6/M7 未定案）、`上游长连接`（M20 只留位）——**但审批与通知表按"目标类型"枚举预留了 `RESOURCE` / `PROMPT`**，将来加表即可接入；
7. **不存二进制内容**（产物只存元数据 + 存储键）。

## 3. 多租户与隔离策略

### 3.1 本期：共享库共享表 + 行级隔离

- 每张租户内业务表都有 `tenant_id BIGINT NOT NULL`；
- 由 **MyBatis-Plus `TenantLineInnerInterceptor`** 自动给 SQL 追加 `tenant_id = ?`，业务代码**不手写**该条件；
- `TenantContext`（ThreadLocal）取值链：**MCP 请求 → api-key → 用户 → 租户**；**管理面 → 登录态（JWT）**；
- ⚠️ **修正（✅ A2 定案 2026-10-15）**：原文写的「**都没有 → 默认租户**」是**危险的降级兜底** —— 它等于"**任何解析失败都放行到默认租户**"。改为：**只有 `auth.mode=dev` 这个显式开关才注入默认租户**；`auth.mode=jwt` 下解析不到租户一律 **`401`**，**永不降级**。（两种写法长得像、后果完全不同，详见 [`前后端交互接口设计.md`](./前后端交互接口设计.md) **4.1.1**）
- **忽略表白名单**（不加租户条件的表）：`mcp_tenant`（ROOT 要管所有租户）、`mcp_config`（含全局行）、登录阶段按 `tenant_code` 查 `mcp_user` 的那条显式 SQL。

### 3.2 逃生舱：物理隔离预留（4 种模式）

| 模式 | 依赖层实现 | 状态 |
| --- | --- | --- |
| `SHARED_TABLE`（共享表 + `tenant_id`） | `TenantLineInnerInterceptor` | ✅ **本期** |
| `TABLE_PREFIX`（`t{n}_mcp_service`） | `DynamicTableNameInnerInterceptor` | 🔒 留钩子 |
| `SCHEMA`（PG `search_path` / MySQL database） | `AbstractRoutingDataSource` + 连接级 schema | 🔒 留钩子 |
| `DATASOURCE`（独立库/实例） | `AbstractRoutingDataSource` 多数据源 | 🔒 留钩子 |

**`mcp_tenant` 已预留三列**：`route_mode` / `schema_name` / `ds_key` —— 切换时**只改数据不改代码结构**。

**切换代价（先说明白）**：迁移 **×N**、连接池 **×N**、备份 **×N**；触发条件只应有两条 —— **客户合规强制物理隔离**，或**单个租户体量独大**。

**迁移路径（因数据模型不变，所以是配置级动作）**：按 `tenant_id` 导出 → 建物理表/schema/库 → 灌数 → 改 `mcp_tenant.route_mode` → 路由生效。无需改 SQL 与实体。

### 3.3 现在必须守住的 5 条约束（否则逃生舱打不开）

| # | 约束 | 为什么 |
| --- | --- | --- |
| 1 | **SQL 不硬编码表名**，一律走实体 `@TableName` | 动态表名才有介入点 |
| 2 | **不建物理外键、不建跨租户唯一键**；唯一索引一律带 `tenant_id` | 否则物理隔离时约束全部失效 |
| 3 | **主键雪花（全局唯一）** | 隔离后不撞 ID，也不需要"每租户一个序列"。✅ **B9 定案（2026-10-15）**：`workerId` 由 **env / StatefulSet 序号**提供（`SNOWFLAKE_WORKER_ID`，取值 0~31），**启动时校验唯一**；**时钟回拨 > 5ms 直接拒绝启动**。**绝不允许两实例同号** —— 同号会在同一毫秒同序号生成**重复主键**，数据互相覆盖**且不报错** |
| 4 | **不写跨租户 JOIN / 跨租户聚合** | 报表只按 `tenant_id` 过滤 |
| 5 | **迁移脚本幂等**，可按租户重复执行 | 物理隔离要跑 N 遍 |

### 3.4 租户解析与降级

```text
MCP 请求：  api-key(token)  →  user  →  tenant        ← 一个 key 只属于一个用户、一个租户
管理面：    JWT             →  user  →  tenant
都取不到：  → 默认租户（mcp_tenant 种子行：id=1, code='default', name='默认租户'，不可删除）
```

**api-key 上线之前的降级路径**：所有请求都落默认租户 → **今天就是"单租户可用"状态**，将来上线只是多填一列，**不改表**。

- 产物签名 URL 的**签名体里带 `tenant_id`**，防猜 `artifactId` 跨租户抓文件；
- 会话与协商版本缓存都以 **token 维度**为键（token 已确定租户，天然隔离）。

## 4. 权限模型

### 4.1 角色（4 个，枚举列，不建角色表）

```text
ROOT（最原始的用户，可创建租户，跨租户）
└── 租户 A ── 超级管理员（租户内最高：管用户、配租户级配置）
    ├── 管理员（增改删 服务/工具/提示词/资源；审批本租户申请）
    └── 用户（申请 api-key；改东西看租户走哪条路）
```

| 动作 | ROOT | 超级管理员 | 管理员 | 用户 |
| --- | --- | --- | --- | --- |
| 创建 / 停用租户 | ✅ | ❌ | ❌ | ❌ |
| 管本租户用户、租户级配置 | ✅ | ✅ | ❌ | ❌ |
| 增改删 服务/工具/提示词/资源 | ✅ | ✅ | ✅ | ❌ → **转申请**（审批模式） |
| 审批变更申请 | — | ✅ | ✅ | ❌ |
| 生成 api-key（点一下就出） | — | ✅ | ✅ | ✅ |
| 可见数据 | 全部 | 全部 | 全部 | **简易：都能见｜审批：只有批准过的可见** |

### 4.2 两条路径（**租户级开关**）

配置键 **`access.change_mode` = `SIMPLE` | `APPROVAL`**（默认 `SIMPLE`）：

- **SIMPLE（简易）**：权限纯看角色。用户没权限就是没权限（只能找管理员改），**数据全租户可见**；
- **APPROVAL（审批）**：用户可提交变更申请，**本租户管理员批准后才生效、才可见**。

> ⚠️ 这条开关**同时决定"能不能改"和"能不能见"**，所以它是租户级配置，不是用户级偏好。

### 4.3 权限判定的唯一入口

```java
// 全部权限判断只走这一个方法，代码里禁止出现散落的 if (role == ADMIN)
public interface PermissionService {
    boolean can(Long userId, Action action, Target target);   // Action: CREATE/UPDATE/DELETE/APPROVE/MANAGE_USER/CONFIG...
}
```

### 4.4 用户组（预留，不建表、不加列）

将来要上用户组：加 `mcp_user_group` + `mcp_user_group_member` 两张表，把 `can()` 的实现从"角色判定"换成"角色 + 组判定"，**调用方一行都不用改**。这就是"预留"的全部 —— **不加投机列**。

### 4.5 登录（SSO 预留）

- **本期：用户名密码 + JWT**；登录凭据为 **`tenant_code` + `username`**（多租户下用户名只在租户内唯一）；
- SSO 预留三列（`auth_source` / `external_id` / `external_provider`），SSO 用户 `password_hash` 为空；将来接 OIDC 只需新增回调接口，**表结构不再变**。

## 5. 审批流（统一草稿式）

### 5.1 形态选型

**采用 (A) 统一草稿式**：变更内容以**完整草稿**存在申请单里，**批准后才写进对象表**。

- 好处：未批准的东西**根本不在对象表里** → "批准过的才可见"**天然成立**；对象表干净、MCP 侧零特判；CREATE / UPDATE / DELETE 三种动作**处理方式统一**；
- 代价：审批模式下"编辑草稿"和"编辑对象"是两个入口（草稿箱在前端）。

### 5.2 6 条不变量（写进服务层，不靠自觉）

| # | 规则 | 落地方式 |
| --- | --- | --- |
| **R1** | **审批中，所有人读到的仍是旧数据** | 草稿式天然满足：对象表不动 |
| **R2** | **同一目标同时只能有一个进行中的申请**（改 / 删）；已有则**拒绝提交** | ⚠️ 避开"部分索引"陷阱（PG 能写 `WHERE status='PENDING'`，**MySQL 没有**）→ 用 **`dedup_key`** 列 + 唯一索引，两库同构（见 5.3） |
| **R3** | **server 有 PENDING → 它下面的所有子对象都不能提交新草稿** | 提交前查 `mcp_change_request` 是否存在 `target_type='SERVICE' AND target_id=父id AND status='PENDING'`（走 `idx_request_parent`） |
| **R4** | **草稿可以随便建，"提交"时才校验**（R2 / R3 / 版本） | 草稿箱在前端本地（本期不建表）；提交才调接口 |
| **R5** | **版本护栏**：批准时若对象 `version` 与草稿的 `base_version` 不一致 → **拒绝批准**，提示"数据已变化，请重新申请" | `base_version INT` + 批准时比对 |
| **R6** | 提交 / 批准 / 驳回 / 撤回 **全程留痕 + 发通知** | 写操作日志（记到人）+ 发通知 |
| **R7** | **批准动作必须原子化**：两个审批人同时点批准，**只能有一个成功** | ✅ **B1 定案（2026-10-15）**：**CAS 条件更新** —— `UPDATE mcp_change_request SET status='APPROVED', … WHERE id=? AND status='PENDING'`；**影响行数 = 0** 说明已被他人批准 → 回 `40901`。**不用** `SELECT … FOR UPDATE`（持锁久、有死锁面）。**MySQL 与 PG 条件更新语义同构** |

> **反向不锁**：子对象有 PENDING 时，父对象（server）仍可改 —— 由 **R5** 在批准环节兜底（不会出现"按旧结构批准了新服务下的工具"）。

### 5.3 `dedup_key`：把"同目标唯一 PENDING"变成双方言同构的唯一索引

```text
PENDING            →  "P:SERVICE:123"      （UPDATE / DELETE：按目标对象）
                   →  "C:TOOL:天气查询"     （CREATE：按 (target_type, 目标 name_norm) 判重）
APPROVED/REJECTED/WITHDRAWN →  "D:<申请单id>"   （每条都已唯一，天然不冲突）
```

唯一索引 **`uk_request_dedup (tenant_id, dedup_key)`** —— 不需要部分索引，MySQL / PG 行为一致。

### 5.4 状态机

```text
PENDING ──批准──> APPROVED（写对象表 / 执行删除，记 applied_at、applied_object_id）
   │
   ├──驳回──> REJECTED
   └──撤回──> WITHDRAWN
```

## 6. 通用约定

| # | 约定 | 说明 |
| --- | --- | --- |
| C1 | **`tenant_id BIGINT NOT NULL`** 出现在每张租户内业务表 | 例外：`mcp_tenant` 自身、`mcp_config` 的全局行（用哨兵 `0`，见 C13） |
| C2 | **主键 `id BIGINT` 雪花**，`ASSIGN_ID` | 不用自增 |
| C3 | **审计列**：`created_at` / `created_by` / `updated_at` / `updated_by` / `version` | `version` 供乐观锁。⚠️ **B2 定案（2026-10-15）**：`version` **必须真的用起来** —— **服务 / 工具 / 标签 / 资源 / 提示词**的**详情响应返回 `version`、`PUT`/删除请求必带**，不一致 → `40901` + 回 `data.current`。**只在审批里用 `baseVersion` 不够**：`SIMPLE` 模式下两个管理员同时改同一工具就是**静默覆盖**（lost update），而这是**必然发生**的。**排除**：`mcp_config`（upsert 语义）、`mcp_user`（低频）→ 不套乐观锁 |
| C4 | **软删除：只留一列 `deleted_seq BIGINT NOT NULL DEFAULT 0`** | 0 = 未删除；删除时写入该行 `id`。**唯一索引一律 `(…, deleted_seq)`** → 可反复删建同名，两库同构。⚠️ 不用 MyBatis-Plus `@TableLogic`（它只写 0/1 标志），逻辑删除统一走一条同构 UPDATE：`SET deleted_seq = id WHERE id = ? AND deleted_seq = 0`。⚠️ **B3 定案（2026-10-15）**：**读路径必须强制带 `deleted_seq = 0`** —— 用**自定义 MyBatis 拦截器统一追加**（**不靠手写公共片段，「人一定会忘」**），并加"漏加即测试红"的 CI 兜底。否则删掉 A 再建同名 B 之后，`selectOne(name)` 命中 2 行 → **`TooManyResultsException` 直接 500** |
| C5 | **`*_norm` 规范化列**（小写 + 去首尾空格 + NFKC） | 唯一判定与 `LIKE` 搜索都打它，**不赌 collation** |
| C6 | **时间** MySQL `DATETIME(3)` / PG `TIMESTAMPTZ(3)`，全部 UTC | Java 侧 `Instant` / `OffsetDateTime` |
| C7 | **JSON 只整存整取**（`JSON` / `JSONB`），**禁止在 SQL 里查 JSON 内部** | 工具定义、草稿、客户端信息 |
| C8 | **不建物理外键** | 软删除 / 批量删除 / 标签合并 / 物理隔离都需要 |
| C9 | 命名全小写下划线、表前缀 `mcp_`、禁保留字、禁给标识符加引号 | 兼容大小写折叠与 `lower_case_table_names` |
| C10 | 参与唯一/比较的列显式 **`utf8mb4_0900_bin`**（PG `COLLATE "C"`） | 与 C5 双保险。⚠️ **B6 定案（2026-10-15）**：**原文写 `utf8mb4_bin` 是错的** —— 它是 **PAD SPACE**（`'ab' = 'ab '` 成立），而 PG `COLLATE "C"` 是 **NO PAD** → **两库语义不等价**，V5「尾空格」用例会两库结果相反。**实测证据（2026-10-15，本机 MySQL 8.0.28）**：`information_schema.COLLATIONS.PAD_ATTRIBUTE` 中 `utf8mb4_bin` = `PAD SPACE`、`utf8mb4_0900_bin` = `NO PAD`。`_0900_*` 需 **MySQL ≥ 8.0.0**（与推荐版本 8.0.30+ 不冲突） |
| C11 | **显式声明隔离级别 = `READ COMMITTED`**（✅ **B8 定案**，不再是"建议"） | MySQL 默认 RR 有间隙锁，PG 默认 RC → **不显式设置就是两库行为分叉**。⚠️ **实测（2026-10-15）**：本机实例**已经是 RC**，而 MySQL **默认是 RR** → **实例默认值根本不可依赖**（换台机器就变），故必须显式设置 **+ CI 断言** |
| C12 | **插件顺序**：`TenantLine` → `DynamicTableName`（预留）→ `Pagination` → `OptimisticLocker` | MyBatis-Plus 官方要求 |
| C13 | **唯一索引里禁止出现可空列** —— 需要"全局 vs 租户"这类维度时用**哨兵值**（如 `tenant_id = 0` 表示全局） | ⚠️ MySQL 与 PG **都**把 NULL 视为互不相等 → 唯一索引会形同失效。**适用范围**：**分类维度列**（`tenant_id` / `scope` —— 每一行都有、且**必须**参与唯一性） |
| **C13a** | **例外（✅ B7 定案 2026-10-15）："条件性唯一"要「有意用 NULL」** —— 当某个唯一性**本来就该"不存在时不约束"**（典型：SSO 的 `external_provider` / `external_id`），**用 NULL，不要填哨兵** | **填哨兵是错的**：把 NULL 换成 `''` 之后，**两个 LOCAL 用户就真的撞了**（C13 本意是防"该管住却管不住"，此处是"本就不该管"）。"唯一索引中任一列为 NULL → 该行不参与唯一性"是 **MySQL / PG 一致**的行为 → **不需要部分索引 / 生成列 / 函数索引**，四库通用（方言差异：PG 有 `WHERE` 部分唯一索引、SQL Server 有 filtered index、**MySQL 与 Oracle 都没有**）。⚠️ **未实测声明（2026-10-15）**：该 NULL 行为**本次未能实证**（MySQL 官网返回 403、本机样本表无 NULL 行；MCP 连接为只读、无法建临时表）→ **按文档记载行为采信**，由 B6/B7 的 Testcontainers CI 卡口兜底验证 |
| C14 | 批量写入分批 **500** 条 | 两侧都有参数/包大小上限 |
| **C15** | **异步 / 跨线程写库禁止读 `TenantContext`** —— **必须把 `tenantId` 当参数显式传进异步任务** | ✅ **B5 定案（2026-10-15）**：调用日志批量落库、通知扇出、`last_used_at` / `download_count` 更新**都是异步的**，而子线程**没有** ThreadLocal 上下文 → **静默落默认租户 = 跨租户串台，且不报错**（最难查的一类 bug）。**不用 `TaskDecorator` 复制上下文** —— 遇到自定义线程池 / MQ / 定时任务就失效；显式入参能在**编译期**逼你想清楚 |
| **C16** | **参数语义必须两处一致**（服务级鉴权 `mcp_service_auth_param` 与 工具级参数 `mcp_tool.request_json`） | 🔄 **2026-10-21 改判：四态 → 三态 + 1 个派生** —— ① `required` / `nonEmpty` / `value` 是**真实开关**；② **`overridable` 不再是开关，恒等于 `(value IS NULL)`**（"给默认值 + 允许覆盖"的组合**已废除** —— 描述与固定值**占同一格**，二者互斥）；③ **服务级鉴权的 `required` / `nonEmpty` 恒 `1`**（**天然必填**，UI 无此二列），**只有工具级参数可配**。映射规则唯一真源见 [`MCP-Server对外接口设计.md`](./MCP-Server对外接口设计.md) **§7.1**，本稿只承载列、**不复制规则** |

**你的定案**：**点一下就生成** → **不设审批状态列**（将来真要审批再加，属破坏性小改）。

> **A6 定案（2026-10-15）· api-key 唯一性 —— 从根上解决与物理隔离的结构性冲突**
>
> **问题根因**（不只是"唯一索引没带 `tenant_id`"）：鉴权链是 `api-key → user → tenant`，**查 token 时还不知道租户** → 这本质上要求一张**跨租户的全局索引**，与 §3.3 约束 2（唯一索引一律带 `tenant_id`，即"禁跨租户唯一键"）**结构性冲突**；逃生舱（`SCHEMA` / `DATASOURCE` / `TABLE_PREFIX`）打开后 `uk_token_hash(token_hash)` 直接失效。
>
> **定案**：**明文 token 内嵌租户标识**，鉴权先定位租户、再查该租户的表 → **全局唯一索引彻底不需要**。
>
> ```text
> 明文 token : mcp_<租户id 的 base36>_<base62(SecureRandom 32 字节)>   ← 熵来自 CSPRNG
> 库里        : token_hash = SHA-256(明文)                             ← 确定性，可查
> 展示        : token_prefix = mcp_<租户id base36>_7f3a               ← 列表里认得出
> 主键        : 雪花（照 C2 不变）                                      ← 编号体系没有新增
> ```
>
> - ✅ **满足"不造数"**：`SecureRandom` 是 JDK 自带，32 字节一把生成，**不需要自增/雪花/分配器**；雪花只继续做 PK；
> - ❌ **熵不能用雪花数**：雪花 = 41 位时间戳 + 10 位 workerId + 12 位序列，**高度可枚举**（知道大致创建时间，单 worker 一天内仅约 400 万候选），且雪花 id 到处出现在 URL 里不保密；**哈希不产生熵** —— `hash(tenantCode + 雪花)` 的熵就等于两者的熵，拿到 `token_hash` 即可离线枚举对撞；
> - **内嵌"租户雪花 id"而非 `tenantCode`**：`tenantCode` 有 `uk_tenant_code`、**允许改名** → 内嵌它会导致"改一次 code，该租户全部 token 失效"；
> - **代价（认下）**：token 明文暴露租户 id —— 可接受（雪花 id 不保密、且 `tenantCode` 本就出现在登录参数里）。
> - **迁移说明（本期无痛）**：本期为设计阶段、**无存量数据** → 格式切换**不涉及数据迁移**。⚠️ 但上线后若再改格式要注意：**旧格式没有租户前缀**，新鉴权路径**无法从 token 定位租户** → 只能回退到全局 `idx_token_hash` 兜底，或强制重签全部 token。

| `origin_name` | VARCHAR(100) | N | 原参数名 |
| `mcp_name` | VARCHAR(100) | N | MCP 参数名 |
| `description` | VARCHAR(500) | Y | 模型可见的描述（**C3 定案：凭据可由调用方传，故此描述确实是给模型看的**） |
| `relation` | VARCHAR(3) | N | `AND` / `OR` —— **组级**逻辑（设计图 #13 的「和/或」），非逐行 |
| `seq` | INT | N | 顺序 |
| **`value`** | VARCHAR(1000) / TEXT | Y | **固定值** —— 🔄 **2026-10-21 定案：与「动态」互斥，不存在"给个默认值但允许覆盖"**。非空 ⇒ **固定模式**（服务端补齐、**不进 `inputSchema`**、`description` 无意义）；读写语义同 `sensitive`（读回 `***`） |
| **`required`** | TINYINT(1) / BOOLEAN | N | ✅ **恒 `1`（2026-10-21 定案：服务级鉴权天然必填，UI 不提供开关）**。语义 = 「**该参数的最终值必须存在**」（写死的 `value` 或调用方传入，二选一），**不是**"调用方必须传"。理由（主人原话）：**没值的鉴权参数毫无意义** |
| **`non_empty`** | TINYINT(1) / BOOLEAN | N | 🔄 **恒 `0`（2026-10-21 晚 · 主人改判："非必填可空更合适"）** —— 服务级鉴权**允许空串**，**不映射 `minLength:1`**。⚠️ 与 `required` 的分工：**「必须有这个参数」看 `required`（恒 1）**；**「参数值可以是空串」看本列（恒 0）** |
| **`overridable`** | TINYINT(1) / BOOLEAN | N | 🔄 **不再独立设置（2026-10-21 改判）：恒等于 `value IS NULL`** —— `value` 非空 ⇒ `0`（固定模式）；`value` 为空 ⇒ `1`（**动态模式**，进 `inputSchema`，`description` **必填**）。⚠️ 原"默认值 + 允许覆盖"语义**已废除** ⇒ 本列已是**冗余列**，长期应删，代码侧按 `value IS NULL` 派生 |
| **`sensitive`** | TINYINT(1) / BOOLEAN | N | **A4 定案：默认 `1`（敏感）** —— 避免新增参数时忘记标。读接口对 `sensitive=1` 一律返回 `***`；**写回 `***` = 保留原值** |

> ⚠️ **本表定位纠正 + 缺口口径定案（2026-10-15）**
>
> **① 本表建模的是「服务级鉴权方式」**（设计图 **#13 服务创建页左下角**）—— `relation`（和/或）+ `seq` + `location` 三列**只存在于该界面**。它**不是**工具级参数面板（#04 请求头/Cookie/Query、#06 请求体 Json，那些在 **`mcp_tool.request_json`**）。两处界面高度相似但**是两个不同的东西**，此前审读曾把它们混为一谈（已更正）。
>
> **② 「和/或」与「天然必填」的关系（✅ 2026-10-21）**：`required` 恒 `1` ⇒ `AND` 组（全部都要有值）语义完全吻合；`OR` 组（至少一个有值）**天然允许组内某参数无值** ⇒ **`OR` 组内的 `required` 按 `0` 处理**（约束是"至少一个"而不是"每个"）。若某组既要"至少一个"又想"每个都有值"，那就是 `AND` —— 用 `relation` 区分即可，不冲突。
>
> **③ 服务级鉴权表的最终列集（✅ 2026-10-21 定案，与设计图一致）**：`类型` / `原参数名` / `MCP 参数名` / **`描述或固定值`（同一格，靠「动态」切换）** / 操作（−）。**不需要** `必填` / `非空` 两列（天然必填），**也不需要** `允许调用方覆盖`（由 `value` 是否为空决定）⇒ **设计图 0 处要改**，此前"需重画加 4 列"的结论**作废**。
>
> **④ `overridable` 已退化为派生列**：`overridable := (value IS NULL)`。**代码不得独立读写该列**，新增/修改时一律由 `value` 是否为空推导。⚠️ 长期看应删列（避免"同一事实两处存"，根因 ②）；本期保留只为兼容已有 DDL 与 API 字段。
>
> **⑤ 与工具级参数的区别**：工具级参数（`mcp_tool.request_json` 里的参数对象）**保留** `required` / `nonEmpty` 独立开关（每个工具参数是否必传确实因工具而异）；**只有服务级鉴权是"天然必填"**。
>
> **⑥ 🔴 `value` 的 `NULL` 与 `''` 不等价（✅ 2026-10-21 晚，随"允许空串"连带 —— 这条必须写进代码）**：`value IS NULL` ⇒ **动态模式**（值由调用方传）；`value = ''` ⇒ **固定模式，且固定值就是空串**（显式向上游传空）。⇒ **派生规则一律用 `IS NULL` 判定，禁止用"是否为空"判空**；**保存/读取时不得把 `''` 归一成 `NULL`**（否则"显式传空"会被错判成"动态"，凭据字段就会意外变成模型可见）。

**索引**：`uk_auth_service_mcpname (tenant_id, service_id, mcp_name, deleted_seq)`｜`idx_auth_service (tenant_id, service_id, seq)`｜`idx_auth_location (tenant_id, location)`

## 12. 配置分层（env 与页面**互不重合**）

### 12.1 一句话判据：这个键该进 env 还是进 DB？

问三个问题，**任一条命中就是 env-only，否则是 DB（`mcp_config`）**：

1. **它是"启动前就得知道"的吗？** —— 连不上 DB 就没法读 DB 里的配置 → **env**
2. **它是密钥吗？**（DB / Redis / S3 凭据、JWT 签名密钥）→ **env**（**本期密钥一律不进页面**；将来若要搬进页面，**必须先标 `isSecret=true`**，见下方 §12.3 尾注 / A4）
3. **它是一台机器一个值、且改了必须整实例一起变吗？**（workerId / 端口 / 监听地址 / 会话存储后端）→ **env**

反过来，**只要是"业务策略"**（谁能改什么、开关、超时、保留天数、上限）→ **DB**，因为它要**热生效**、要**可按租户覆盖**、要**留操作日志**。

> 🔒 **互不重合是硬约束**：同一个键**绝不允许两边都出现** —— 那就是 **C17 那种"一个事实两处写法"**（见 [`设计决策记录.md`](./设计决策记录.md) §6.5）。**新增任何配置项，必须先在本节登记归属。**

**命名约定**：① **Spring Boot 原生键沿用原生名**（`SERVER_PORT` / `SPRING_PROFILES_ACTIVE`），不另起名、不多一层映射；② **自有键统一 `MCP_` 前缀**；③ ⚠️ **两个历史键保留原名不改** —— `SSRF_ALLOWED_PORTS`（A3）、`SNOWFLAKE_WORKER_ID`（B9），它们已被多处文档引用；若主人要求统一前缀，可一次性改名（成本 ≈ 改 3 处引用）。

### 12.4 通则：安全类配置「缺省即最严」

> **起源**：主人问「**如果某个租户它就完全不配置安全呢？**」—— 这一问挖出**两处 fail-open**（缺省即最松），故立此通则。

**安全相关的东西分三类，只有 ① 类是天生安全的：**

| 类别 | 例子 | 租户"完全不配置"时会怎样 |
| --- | --- | --- |
| **① 不可配置的底线**（硬编码 / env-only） | 密码强度（≥8 位含字母数字）、失败锁定（5 次 / 15 分钟）、**BCrypt cost 12**、SSRF 全套、`tenant_id` 强制注入、审计日志 | ✅ **永远是严的** —— 租户**连"关掉"的入口都没有**（A2 的 `auth.mode`、A5 的密码策略都属于此类） |
| **② 可配置，但缺省即最严** | `auth.console_jwt_ttl_minutes`（缺省 **7 天**）、`artifact.ttl_hours`、`log.retention_days` | ✅ 落到**最保守的合理值** |
| **③ 可配置，且缺省即最松** ⚠️ | `mcp_client_token.expires_at`（NULL = 永不过期）**← 已修，见 §8.3** | ❌ **不配 = 永久凭据** |

**规则（新增配置项时逐条自问）：**

1. **它能不能"不配就变松"？** 能 → **必须改成 ②**（补一个安全默认值），或干脆降级为 ①（**不做成配置项**）。
2. **"放宽"必须显式** —— 要永久 / 要关防护，**必须传一个明确的特殊值**（如 `neverExpires=true`）；**不允许用"省略"来表达放宽**。
3. **放宽必须留痕** —— 界面**醒目警告** + **写审计日志**（记到人）。
4. **兜底永远不许"降级放行"** —— 解析失败 → **`401`**，**绝不落默认租户**（A2 已定案，见 §3.1 的修正）。

**已按此通则修掉的两处**：① `mcp_client_token.expires_at` 的「省略即永久」（**§8.3**）；② 控制台 JWT 的「不配即永久」疑虑（**§12.3** 缺省 7 天）。

## 15. 删除与级联策略（应用层，无物理外键）

| 动作 | 处理 |
| --- | --- |
| 删除 / 停用**租户** | 租户 `status=SUSPENDED`（**默认租户不可停**）；数据保留，登录与 MCP 调用全部拒绝 |
| 删除**用户** | `deleted_seq=id`；其 api-key **同步禁用**（`status=DISABLED`），已签发产物按自身 `expires_at` 过期 |
| 删除**服务** | 同事务：服务软删除 → 其工具一并软删除 → 服务-标签关联物理删除 → 写日志 |
| 删除**工具** | 软删除 + 日志；历史产物自然过期 |
| **合并标签** | 事务：改挂关联 → 源标签软删除；`409` 时整体回滚 |
| **审批生效** | 批准 `CREATE` → 建对象（记 `applied_object_id`）；批准 `UPDATE` → 整量替换 + `version+1`；批准 `DELETE` → 软删除。**全部在同事务内**，并写日志 + 发通知 |
| **审批中对象被直接改**（管理员在审批模式下直改） | 草稿 `base_version` 失配 → **批准时拒绝**（R5） |
| 导入会话 / 通知 / 产物 / 日志 | 到期由任务清理：**先 `SELECT id … LIMIT n` 再 `DELETE … IN`**（避开 `DELETE … LIMIT` 方言差异）；产物**先删文件后删行**（防孤儿） |

### 15.1 清理任务是唯一允许跨租户的写操作（✅ **B4 定案**，2026-10-15）

导入会话 / 产物 / 通知 / 日志四个清理任务是**跨租户 `DELETE`**，而租户插件会给**所有** SQL 自动追加 `tenant_id` → 轻则"**只清默认租户**"（垃圾越积越多）、重则配上忽略表白名单后**误清全库**。

**定案**：清理走**专用 Mapper**（独立 `SqlSessionFactory`，**不进租户插件**），并把这几张表登记进**「清理专用忽略白名单」** —— 与 §3.1 的**业务**忽略表**分开管理**，避免顺手把业务表也扩进白名单。

**验收**：造 2 个租户各自的过期行 → **两个租户的行都被清掉**，且**未过期的行一条不动**。

**🔴 产物清理必须按 `storage_type` 分派（✅ 2026-10-21 补，A23 连带缺口）**

| `storage_type` | 怎么删 | 注意 |
| --- | --- | --- |
| `LOCAL` | 删 `MCP_STORAGE_LOCAL_ROOT` 下 `storage_key` 对应的文件 | **文件已不存在 → 视为成功**（幂等；别因一次 404 卡死整批） |
| `S3`（二期） | 调对象存储 `DeleteObject(bucket, storage_key)` | `NoSuchKey` → **同样视为成功**（幂等） |

顺序固定为 **先删存储对象、后删行**（同 §15 总表）：反过来的话「删行成功、删文件失败」= **孤儿文件永远清不掉**（已无元数据可查）。
🔴 **禁止**按"表里全是 `LOCAL`"把实现写死 —— 否则二期一接 S3，**S3 上的对象将永远不回收**（存储只增不减，且没人发现）。
