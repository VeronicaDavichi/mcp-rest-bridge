# 数据库设计（多租户版）

> 覆盖：**多租户**底座（租户 / 用户 / 权限）+ 控制台业务表（服务 / 工具 / 标签 / 导入）+ 审批流 + 通知 + 分层配置 + MCP 运行时表（api-key、可见范围、日志、产物、可选会话与协商版本缓存）。

> 隔离策略：**共享库共享表 + `tenant_id`**，但**依赖层预留物理表隔离的逃生舱**（第 3 章）。
> 状态：**v0.2 多租户版**。⚠️ 其中**9 条是我按推荐值替你定的**，集中列在**第 19 章**，任一条不顺眼直接说。

## 1. 目标、边界与不做什么

**做**：多租户行级隔离的完整表结构、角色与权限模型、审批流（草稿式）、通知、分层配置、索引、迁移组织、级联策略、数据字典、验收标准。

**不做（本期）**：

1. **不做物理隔离的落地实现**（只留逃生舱：4 种模式 + 5 条必须守住的约束，见 3.2 / 3.3）；
2. **不做用户组**（只留权限判定抽象点 `PermissionService.can()`，见 4.4）；
3. **不做 api-key 审批流**（你的定案：**点一下就生成**）；
4. **不做分库分表 / 分区**；日志靠时间索引 + 应用层归档；
5. **不建物理外键**；
6. **不建"无功能设计"的表**：`资源` / `提示词`（M6/M7 未定案）、`上游长连接`（M20 只留位）——**但审批与通知表按"目标类型"枚举预留了 `RESOURCE` / `PROMPT`**，将来加表即可接入；
7. **不存二进制内容**（产物只存元数据 + 存储键）。

## 3. 多租户与隔离策略

### 3.1 本期：共享库共享表 + 行级隔离

- 每张租户内业务表都有 `tenant_id BIGINT NOT NULL`；
- 由 **MyBatis-Plus `TenantLineInnerInterceptor`** 自动给 SQL 追加 `tenant_id = ?`，业务代码**不手写**该条件；
- `TenantContext`（ThreadLocal）取值链：**MCP 请求 → api-key → 用户 → 租户**；**管理面 → 登录态（JWT）**；**都没有 → 默认租户**；
- **忽略表白名单**（不加租户条件的表）：`mcp_tenant`（ROOT 要管所有租户）、`mcp_config`（含全局行）、登录阶段按 `tenant_code` 查 `mcp_user` 的那条显式 SQL。

### 3.2 逃生舱：物理隔离预留（4 种模式）

| 模式 | 依赖层实现 | 状态 |
| --- | --- | --- |
| `SHARED_TABLE`（共享表 + `tenant_id`） | `TenantLineInnerInterceptor` | ✅ **本期** |
| `TABLE_PREFIX`（`t{n}_mcp_service`） | `DynamicTableNameInnerInterceptor` | 🔒 留钩子 |
| `SCHEMA`（PG `search_path` / MySQL database） | `AbstractRoutingDataSource` + 连接级 schema | 🔒 留钩子 |
| `DATASOURCE`（独立库/实例） | `AbstractRoutingDataSource` 多数据源 | 🔒 留钩子 |

**`mcp_tenant` 已预留三列**：`route_mode` / `schema_name` / `ds_key` —— 切换时**只改数据不改代码结构**。

**切换代价（先说明白）**：迁移 **×N**、连接池 **×N**、备份 **×N**；触发条件只应有两条 —— **客户合规强制物理隔离**，或**单个租户体量独大**。

**迁移路径（因数据模型不变，所以是配置级动作）**：按 `tenant_id` 导出 → 建物理表/schema/库 → 灌数 → 改 `mcp_tenant.route_mode` → 路由生效。无需改 SQL 与实体。

### 3.3 现在必须守住的 5 条约束（否则逃生舱打不开）

| # | 约束 | 为什么 |
| --- | --- | --- |
| 1 | **SQL 不硬编码表名**，一律走实体 `@TableName` | 动态表名才有介入点 |
| 2 | **不建物理外键、不建跨租户唯一键**；唯一索引一律带 `tenant_id` | 否则物理隔离时约束全部失效 |
| 3 | **主键雪花（全局唯一）** | 隔离后不撞 ID，也不需要"每租户一个序列" |
| 4 | **不写跨租户 JOIN / 跨租户聚合** | 报表只按 `tenant_id` 过滤 |
| 5 | **迁移脚本幂等**，可按租户重复执行 | 物理隔离要跑 N 遍 |

### 3.4 租户解析与降级

```text
MCP 请求：  api-key(token)  →  user  →  tenant        ← 一个 key 只属于一个用户、一个租户
管理面：    JWT             →  user  →  tenant
都取不到：  → 默认租户（mcp_tenant 种子行：id=1, code='default', name='默认租户'，不可删除）
```

**api-key 上线之前的降级路径**：所有请求都落默认租户 → **今天就是"单租户可用"状态**，将来上线只是多填一列，**不改表**。

- 产物签名 URL 的**签名体里带 `tenant_id`**，防猜 `artifactId` 跨租户抓文件；
- 会话与协商版本缓存都以 **token 维度**为键（token 已确定租户，天然隔离）。

## 4. 权限模型

### 4.1 角色（4 个，枚举列，不建角色表）

```text
ROOT（最原始的用户，可创建租户，跨租户）
└── 租户 A ── 超级管理员（租户内最高：管用户、配租户级配置）
    ├── 管理员（增改删 服务/工具/提示词/资源；审批本租户申请）
    └── 用户（申请 api-key；改东西看租户走哪条路）
```

| 动作 | ROOT | 超级管理员 | 管理员 | 用户 |
| --- | --- | --- | --- | --- |
| 创建 / 停用租户 | ✅ | ❌ | ❌ | ❌ |
| 管本租户用户、租户级配置 | ✅ | ✅ | ❌ | ❌ |
| 增改删 服务/工具/提示词/资源 | ✅ | ✅ | ✅ | ❌ → **转申请**（审批模式） |
| 审批变更申请 | — | ✅ | ✅ | ❌ |
| 生成 api-key（点一下就出） | — | ✅ | ✅ | ✅ |
| 可见数据 | 全部 | 全部 | 全部 | **简易：都能见｜审批：只有批准过的可见** |

### 4.2 两条路径（**租户级开关**）

配置键 **`access.change_mode` = `SIMPLE` | `APPROVAL`**（默认 `SIMPLE`）：

- **SIMPLE（简易）**：权限纯看角色。用户没权限就是没权限（只能找管理员改），**数据全租户可见**；
- **APPROVAL（审批）**：用户可提交变更申请，**本租户管理员批准后才生效、才可见**。

> ⚠️ 这条开关**同时决定"能不能改"和"能不能见"**，所以它是租户级配置，不是用户级偏好。

### 4.3 权限判定的唯一入口

```java
// 全部权限判断只走这一个方法，代码里禁止出现散落的 if (role == ADMIN)
public interface PermissionService {
    boolean can(Long userId, Action action, Target target);   // Action: CREATE/UPDATE/DELETE/APPROVE/MANAGE_USER/CONFIG...
}
```

### 4.4 用户组（预留，不建表、不加列）

将来要上用户组：加 `mcp_user_group` + `mcp_user_group_member` 两张表，把 `can()` 的实现从"角色判定"换成"角色 + 组判定"，**调用方一行都不用改**。这就是"预留"的全部 —— **不加投机列**。

### 4.5 登录（SSO 预留）

- **本期：用户名密码 + JWT**；登录凭据为 **`tenant_code` + `username`**（多租户下用户名只在租户内唯一）；
- SSO 预留三列（`auth_source` / `external_id` / `external_provider`），SSO 用户 `password_hash` 为空；将来接 OIDC 只需新增回调接口，**表结构不再变**。

## 5. 审批流（统一草稿式）

### 5.1 形态选型

**采用 (A) 统一草稿式**：变更内容以**完整草稿**存在申请单里，**批准后才写进对象表**。

- 好处：未批准的东西**根本不在对象表里** → "批准过的才可见"**天然成立**；对象表干净、MCP 侧零特判；CREATE / UPDATE / DELETE 三种动作**处理方式统一**；
- 代价：审批模式下"编辑草稿"和"编辑对象"是两个入口（草稿箱在前端）。

### 5.2 6 条不变量（写进服务层，不靠自觉）

| # | 规则 | 落地方式 |
| --- | --- | --- |
| **R1** | **审批中，所有人读到的仍是旧数据** | 草稿式天然满足：对象表不动 |
| **R2** | **同一目标同时只能有一个进行中的申请**（改 / 删）；已有则**拒绝提交** | ⚠️ 避开"部分索引"陷阱（PG 能写 `WHERE status='PENDING'`，**MySQL 没有**）→ 用 **`dedup_key`** 列 + 唯一索引，两库同构（见 5.3） |
| **R3** | **server 有 PENDING → 它下面的所有子对象都不能提交新草稿** | 提交前查 `mcp_change_request` 是否存在 `target_type='SERVICE' AND target_id=父id AND status='PENDING'`（走 `idx_request_parent`） |
| **R4** | **草稿可以随便建，"提交"时才校验**（R2 / R3 / 版本） | 草稿箱在前端本地（本期不建表）；提交才调接口 |
| **R5** | **版本护栏**：批准时若对象 `version` 与草稿的 `base_version` 不一致 → **拒绝批准**，提示"数据已变化，请重新申请" | `base_version INT` + 批准时比对 |
| **R6** | 提交 / 批准 / 驳回 / 撤回 **全程留痕 + 发通知** | 写操作日志（记到人）+ 发通知 |

> **反向不锁**：子对象有 PENDING 时，父对象（server）仍可改 —— 由 **R5** 在批准环节兜底（不会出现"按旧结构批准了新服务下的工具"）。

### 5.3 `dedup_key`：把"同目标唯一 PENDING"变成双方言同构的唯一索引

```text
PENDING            →  "P:SERVICE:123"      （UPDATE / DELETE：按目标对象）
                   →  "C:TOOL:天气查询"     （CREATE：按 (target_type, 目标 name_norm) 判重）
APPROVED/REJECTED/WITHDRAWN →  "D:<申请单id>"   （每条都已唯一，天然不冲突）
```

唯一索引 **`uk_request_dedup (tenant_id, dedup_key)`** —— 不需要部分索引，MySQL / PG 行为一致。

### 5.4 状态机

```text
PENDING ──批准──> APPROVED（写对象表 / 执行删除，记 applied_at、applied_object_id）
   │
   ├──驳回──> REJECTED
   └──撤回──> WITHDRAWN
```

## 6. 通用约定

| # | 约定 | 说明 |
| --- | --- | --- |
| C1 | **`tenant_id BIGINT NOT NULL`** 出现在每张租户内业务表 | 例外：`mcp_tenant` 自身、`mcp_config` 的全局行（用哨兵 `0`，见 C13） |
| C2 | **主键 `id BIGINT` 雪花**，`ASSIGN_ID` | 不用自增 |
| C3 | **审计列**：`created_at` / `created_by` / `updated_at` / `updated_by` / `version` | `version` 供乐观锁 |
| C4 | **软删除：只留一列 `deleted_seq BIGINT NOT NULL DEFAULT 0`** | 0 = 未删除；删除时写入该行 `id`。**唯一索引一律 `(…, deleted_seq)`** → 可反复删建同名，两库同构。⚠️ 不用 MyBatis-Plus `@TableLogic`（它只写 0/1 标志），逻辑删除统一走一条同构 UPDATE：`SET deleted_seq = id WHERE id = ? AND deleted_seq = 0` |
| C5 | **`*_norm` 规范化列**（小写 + 去首尾空格 + NFKC） | 唯一判定与 `LIKE` 搜索都打它，**不赌 collation** |
| C6 | **时间** MySQL `DATETIME(3)` / PG `TIMESTAMPTZ(3)`，全部 UTC | Java 侧 `Instant` / `OffsetDateTime` |
| C7 | **JSON 只整存整取**（`JSON` / `JSONB`），**禁止在 SQL 里查 JSON 内部** | 工具定义、草稿、客户端信息 |
| C8 | **不建物理外键** | 软删除 / 批量删除 / 标签合并 / 物理隔离都需要 |
| C9 | 命名全小写下划线、表前缀 `mcp_`、禁保留字、禁给标识符加引号 | 兼容大小写折叠与 `lower_case_table_names` |
| C10 | 参与唯一/比较的列显式 `utf8mb4_bin`（PG `COLLATE "C"`） | 与 C5 双保险 |
| C11 | **显式声明隔离级别**（建议 READ COMMITTED，与 PG 默认一致） | MySQL 默认 RR 有间隙锁 |
| C12 | **插件顺序**：`TenantLine` → `DynamicTableName`（预留）→ `Pagination` → `OptimisticLocker` | MyBatis-Plus 官方要求 |
| C13 | **唯一索引里禁止出现可空列** —— 需要"全局 vs 租户"这类维度时用**哨兵值**（如 `tenant_id = 0` 表示全局） | ⚠️ MySQL 与 PG **都**把 NULL 视为互不相等 → 唯一索引会形同失效 |
| C14 | 批量写入分批 **500** 条 | 两侧都有参数/包大小上限 |

## 8. 逐表设计

> 除特别说明，每表都含 C1 的 `tenant_id` 与 C3 的审计列（`created_at` / `created_by` / `updated_at` / `updated_by` / `version`）；软删除表再含 C4 的 `deleted_seq`。下面只列**其余业务列**。

### 8.1 `mcp_tenant`（租户）

| 列 | 类型 | 空 | 默认 | 说明 |
| --- | --- | --- | --- | --- |
| `id` | BIGINT | N | - | 雪花；`id=1` 为**默认租户**（种子行，不可删除） |
| `code` | VARCHAR(50) | N | - | 租户编码（登录用，**小写存储**，如 `acme`） |
| `name` | VARCHAR(100) | N | - | 租户名称 |
| `name_norm` | VARCHAR(100) | N | - | 规范化名 |
| `status` | VARCHAR(10) | N | 'ACTIVE' | `ACTIVE` / `SUSPENDED` |

## 10. 索引与查询模式映射

| 接口 / 场景 | 查询模式 | 依赖索引 |
| --- | --- | --- |
| 登录 | `tenant_code` + `username` 定位用户 | `uk_tenant_code` + `uk_user_username`（**显式 WHERE，绕过租户插件**） |
| `GET /services`（搜索 / 标签筛选 / 翻页） | `name_norm LIKE '%kw%'` + 标签 `IN` | `idx_st_tag`；⚠️ 前导通配无索引可用，靠租户内数据量（百级）兜住 |
| 服务唯一性校验 | `name_norm` + `deleted_seq` | `uk_service_name` |
| 批量改状态 / 删除 | `WHERE id IN (…)` | PK |
| `POST /tags/rename`（合并） | 改挂 + 软删除 + `409` 判定 | `uk_tag_name` + `idx_st_tag` |
| `GET /tools`（多条件翻页） | 服务 / 方法 / 状态组合 | `idx_tool_service`、`idx_tool_method`、`idx_tool_enabled` |
| 导入 commit | **事务**：写工具 + 更新会话 + 日志 | `uk_tool_name` |
| 导入 / 产物 / 通知 / 日志 清理 | `expires_at < now` 先 `SELECT id … LIMIT` 再 `DELETE IN` | `idx_import_expire`、`idx_artifact_expire`、`idx_notif_expire`、`idx_log_created` |
| **提交变更申请** | 查 R2（`dedup_key`）+ R3（父申请） | `uk_request_dedup`、`idx_request_parent` |
| 批准 | 读申请 → 校验 `base_version` → 写对象 → 更新申请 → 发通知 | PK + 对象 `version` |
| 通知列表 / 未读数 | `user_id` + `dismissed_at IS NULL` | `idx_notif_user` |
| 首页流量图 | 时间范围分桶 | `idx_log_created` |
| 配置读取 | `(scope, tenant_id, key)` | `uk_config` |

## 12. 配置分层（env 与页面**互不重合**）

### 12.1 两张互斥清单

| 分区 | 谁管 | 内容 | 生效 |
| --- | --- | --- | --- |
| **env-only（引导类）** | 运维 / 部署 | 数据库与 Redis 连接、端口、密钥、存储根路径（本机 / S3）、日志级别、会话存储类型、雪花 workerId | 改完**重启** |
| **page-managed（策略类）** | 管理员（将来页面） | `access.change_mode`、文件接口开关（=方言上限）、上游默认超时、日志保留天数、通知保留天数、导入文件大小上限 | **热生效**（缓存失效） |

### 12.2 生效链（因为互不重合，所以不会打架）

```text
page-managed 键：  租户级  >  全局（mcp_config, tenant_id=0）  >  代码内置默认值   ← 不读 env
env-only   键：    env    >  代码内置默认值                                    ← 页面永不出现
```

### 12.3 已登记的 page-managed 键

| `config_key` | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `access.change_mode` | ENUM | `SIMPLE` | `SIMPLE` / `APPROVAL`（4.2） |

**规则**：`config_key` **必须来自枚举白名单**；每次改动写操作日志（记到人）；缓存单机内存 + TTL，多实例用 Redis 广播失效。

- `spring.flyway.locations` 按 profile 指向 `db/migration/{mysql|postgresql}`；
- **两套完整 DDL**（不共用 `common`，避免跨 location 撞版本号）；只允许"类型映射 + `COLLATE`"这类语义等价差异；

## 15. 删除与级联策略（应用层，无物理外键）

| 动作 | 处理 |
| --- | --- |
| 删除 / 停用**租户** | 租户 `status=SUSPENDED`（**默认租户不可停**）；数据保留，登录与 MCP 调用全部拒绝 |
| 删除**用户** | `deleted_seq=id`；其 api-key **同步禁用**（`status=DISABLED`），已签发产物按自身 `expires_at` 过期 |
| 删除**服务** | 同事务：服务软删除 → 其工具一并软删除 → 服务-标签关联物理删除 → 写日志 |
| 删除**工具** | 软删除 + 日志；历史产物自然过期 |
| **合并标签** | 事务：改挂关联 → 源标签软删除；`409` 时整体回滚 |
| **审批生效** | 批准 `CREATE` → 建对象（记 `applied_object_id`）；批准 `UPDATE` → 整量替换 + `version+1`；批准 `DELETE` → 软删除。**全部在同事务内**，并写日志 + 发通知 |
| **审批中对象被直接改**（管理员在审批模式下直改） | 草稿 `base_version` 失配 → **批准时拒绝**（R5） |
| 导入会话 / 通知 / 产物 / 日志 | 到期由任务清理：**先 `SELECT id … LIMIT n` 再 `DELETE … IN`**（避开 `DELETE … LIMIT` 方言差异）；产物**先删文件后删行**（防孤儿） |
