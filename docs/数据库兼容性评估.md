# 数据库兼容性评估：MySQL 与 PostgreSQL 双支持（v0.1）

> 评估对象：**MCP REST Bridge** 产品自身的管理面数据库（服务 / 工具 / 资源 / 提示词 / 标签 / 导入会话 / 操作日志 / Token 等）。
> 评估目标：**同一套代码同时支持 MySQL 与 PostgreSQL**，包括 DDL、SQL、驱动、迁移脚本、测试与运维。
> 状态：**评估稿（未定案）** —— 结论分「零成本 / 小成本 / 大成本」三档，路线由人拍板（见 §7）。

## 1. 目标、边界与不做什么

**做**：
1. 说清"双支持"的真实代价落在哪几处（不是"连得上"的问题）；
2. 给出**可执行的禁止清单**与**收敛机制**，让日常开发不产生方言债；
3. 给出**可验收**的判定标准（CI 能卡、脚本能比）。

**不做（本期不在范围）**：
1. **不设计表结构**（字段级 DB 设计仍待接口过审后单独出）；
2. **不做跨库数据同步 / 双写** —— 目标形态是"**部署时选一个库**，同一套代码都能跑"；
3. **不做数据库级全文检索**（见 §3.11，建议规避）；
4. **不评估 NoSQL**（Redis 仅在 M12 会话存储里作为可选项，另议）；
5. **不承诺 MySQL 5.7**（见 §2 假设 1，若必须支持需重估）。

## 2. 前提与假设（凡假设必写影响）

| # | 假设 | 若不符的影响 |
| --- | --- | --- |
| 1 | ✅ **MySQL 最低 `8.0.30+`**（**Q1 已定案**；原文"8.0.13+"**作废**，2026-10-21 统一） | 若必须 5.7：**无 CTE / 无窗口函数 / 无函数索引 / 无 `SKIP LOCKED` / `CHECK` 不生效** → SQL 层开销 **+30%~50%**，且 5.7 已停止支持，**建议直接拒绝**。⚠️ **为什么抬到 8.0.30**：`utf8mb4_0900_bin`（**B6**）与后续 DDL 特性都以 8.0.30 为基线 —— **两个版本口径长期并存本身就是根因 ②「同一事实两处写法」的典型**，故此处统一为定案值 |
| 2 | **PostgreSQL 最低 13+**（推荐 16） | 12 以下少了部分 `jsonb` 能力改进与 `gen_random_uuid()` 内建（13+） |
| 3 | 持久层 **MyBatis-Plus**（+ MyBatis XML） | 若换 JPA/Hibernate：方言自动适配更强，但本评估的分支机制（`databaseId`）需改写法 |

| 5 | **无跨库 JOIN、无存储过程、无触发器** | 一旦引入，成本翻倍且需双份实现 |
| 6 | **时间统一 UTC 存储**，应用层生成 | 若依赖 DB 的 `NOW()`/`ON UPDATE`，方言差异立刻出现 |
| 7 | 二进制产物**不进库**（本机 / S3，见 M5/M22） | 若进库：`LONGBLOB` vs `bytea` + 大字段索引限制，成本上升 |
| 8 | 部署形态 = **一套代码 + 一个库**（同构部署） | 若要求"同实例同时连两个库"，超出本评估范围 |

## 3. 兼容矩阵（只列本项目真会用到的东西）

图例：✅ 两边同构（零成本）｜🟡 有差异但收敛容易｜🔴 真差异，必须双写或规避

| # | 能力 | MySQL 8.0 | PostgreSQL 14+ | 判定 | 本项目的用法与取舍 |
| --- | --- | --- | --- | --- | --- |
| 3.1 | 分页 | `LIMIT ? OFFSET ?` | 同 | ✅ | MyBatis-Plus `PaginationInnerInterceptor` 按 `DbType` 自动出方言 SQL；**手写分页也能同构** |
| 3.2 | 主键生成 | `AUTO_INCREMENT` | `GENERATED … AS IDENTITY` / `serial` | 🟡 | **定案建议：应用层生成（雪花 / ULID / `IdType.ASSIGN_ID`）** → 彻底绕开；若用自增，JDBC `useGeneratedKeys` 两边都能拿到 |
| 3.3 | Upsert | `INSERT … ON DUPLICATE KEY UPDATE` | `INSERT … ON CONFLICT (…) DO UPDATE` | 🔴 | **无语义等价的一行语法**。本项目用点：导入 commit 幂等、配置项写入、标签合并 → 走**方言分支**（见 §5.3） |
| 3.4 | 插入后取回 | 无 `RETURNING` | `INSERT … RETURNING` | 🟡 | 统一用 `useGeneratedKeys`，不用 `RETURNING` |
| 3.5 | 布尔 | `TINYINT(1)` / `BOOLEAN` 别名 | 原生 `BOOLEAN` | ✅ | DDL 不同、JDBC 映射一致 |
| 3.6 | 时间与时区 | `DATETIME(3)`（无时区）/ `TIMESTAMP`（**2038 上限、随会话时区转换**） | `timestamptz`（存 UTC，无上限） | 🔴 | **语义差异最大的一处**。约定：**应用层生成 UTC**，Java 侧统一 `Instant`/`OffsetDateTime`，**禁止** DB 端 `NOW()`、`ON UPDATE CURRENT_TIMESTAMP`（后者 MySQL 专属） |
| 3.7 | JSON 存储 | `JSON`（8.0，不能直接建索引，需生成列） | `JSON` / `JSONB`（可 GIN 索引） | 🟡 | 我们把 `inputSchema`/`outputSchema`/参数定义当**整块 JSON 存**，**只存不查** → 两边都可用；**禁止在 SQL 里查 JSON 内部**（`JSON_EXTRACT` / `->>` / `@>`） |
| 3.8 | 软删除 + 唯一约束 | **无部分索引** | `CREATE UNIQUE INDEX … WHERE deleted_at IS NULL` | 🔴 | 真差异。**同构解法（推荐）**：唯一索引改为 `UNIQUE(name, deleted_seq)`，`deleted_seq=0` 表示未删除、删除时写入该行 id（或删除时间戳）→ 两库行为完全一致（见 §6.2） |
| 3.9 | 函数 / 表达式索引 | 8.0.13+ 支持函数键部分 `((lower(name)))`；更老需生成列（⚠️ 这是**该特性引入的版本**，**不是我们的最低门槛** —— 门槛见 **Q1 = 8.0.30+**） | 直接支持 | 🟡 | 若做"名称不区分大小写唯一"，**优先用 §6.2 的规范化列方案**（存 `name_norm` 小写列 + 普通唯一索引）→ 比函数索引更省事、两库同构 |
| 3.10 | **字符串比较语义（最易踩）** | 默认 `utf8mb4_0900_ai_ci`：**大小写不敏感 + 重音不敏感**，且 `_0900_*` 是 **NO PAD**（尾空格有意义）；老 `utf8mb4_general_ci` 是 PAD SPACE（尾空格被忽略） | 默认**区分大小写**（取决于建库 locale，如 `en_US.UTF-8`） | 🔴 | **同一份"名称唯一"逻辑在两库行为不同** → 必须**显式指定 collation** 或**用规范化列**（推荐后者，见 §6.2）。✅ **B6 定案（2026-10-15）**：唯一 / 比较列统一用 **`utf8mb4_0900_bin`**（**NO PAD**，对齐 PG `COLLATE "C"`）—— **原文与 DB 稿 C10 写的 `utf8mb4_bin` 是 PAD SPACE，语义不等价，已改**。**实测证据（2026-10-15，MySQL 8.0.28）**：`information_schema.COLLATIONS.PAD_ATTRIBUTE` → `utf8mb4_bin` = `PAD SPACE`、`utf8mb4_0900_bin` = `NO PAD`、`utf8mb4_0900_ai_ci` = `NO PAD` |
| 3.11 | 全文检索（中文） | `FULLTEXT` + 内置 `ngram` 解析器 | 需扩展（`zhparser` / `pg_jieba`）或 `pg_trgm` | 🔴 | **建议不做**：搜索走"名称/描述 `LIKE` + 应用层过滤"，或未来上 ES。若强做，等于两套实现 + 两套中文分词运维 |
| 3.12 | `LIKE` 大小写 | 跟随 collation（默认不敏感） | 区分大小写，不敏感需 `ILIKE` | 🔴 | 搜索行为会不一致 → **统一查规范化列**（`name_norm LIKE ?`，参数也在应用层小写化） |
| 3.13 | `NULL` 排序 | **不支持 `NULLS LAST`** | 支持 | 🟡 | 若排序字段可空（如 `last_called_at`），需分支或**用非空默认值**规避（推荐：`NOT NULL DEFAULT`） |
| 3.14 | `DELETE … LIMIT` | 支持 | **不支持** | 🔴 | 用于 TTL 清理（导入会话、会话存储、产物元数据）→ 同构写法：先 `SELECT id … LIMIT n` 再 `DELETE … IN (…)`（两库一致，代价是多一次往返） |
| 3.15 | `SKIP LOCKED` | 8.0+ | 9.5+ | ✅ | 若做任务领取可用；5.7 不可用 |
| 3.16 | CTE / 窗口函数 | 8.0+ | ✅ | ✅ | 项目内可用（但保持简单，`jsqlparser` 解析方言偶有边界） |
| 3.17 | `CHECK` 约束 | 8.0.16+ 真正生效 | ✅ | ✅ | 老版本会被静默忽略 → 业务校验不要只靠 DB |
| 3.18 | 字符串拼接 / 聚合 / 格式化 | `CONCAT`；`GROUP_CONCAT`；`DATE_FORMAT` | `\|\|` / `CONCAT`；`string_agg`；`to_char` | 🟡 | **禁止清单**：不在 SQL 里做聚合拼接与时间格式化（放应用层） |
| 3.19 | 标识符大小写 / 保留字 | 表名在 Linux 默认**区分大小写**（`lower_case_table_names=0`）；用反引号 | 未加引号**折叠为小写**；用双引号 | 🟡 | 约定：**全小写下划线命名，禁用保留字当列名，禁止给标识符加引号** |
| 3.20 | 字符集 | 必须 `utf8mb4`（`utf8` 是三字节，存不了 emoji） | UTF8 无此坑 | ✅ | MySQL 建库建表统一 `utf8mb4` + 显式 collation |
| 3.21 | 大文本 / 索引长度 | `TEXT` 建索引需前缀长度；InnoDB + `utf8mb4` 索引键上限约 **3072 字节** | `text` 可直接索引；btree 单键约 **2704 字节** | 🟡 | 名称类字段定长 `VARCHAR(200)` 以内（跨库安全），长描述用 `TEXT` 且不建唯一索引 |
| 3.22 | 事务隔离级别 | 默认 **REPEATABLE READ**（间隙锁） | 默认 **READ COMMITTED** | 🔴 | 并发语义不同（幻读/死锁概率）→ **必须显式声明隔离级别**并写进开发约定。✅ **B8 定案（2026-10-15）**：**定 RC**（显式设置 + CI 断言）。⚠️ **实测**：本机 MySQL 实例**已经是 RC**，而 **MySQL 默认是 RR** → **实例默认值根本不可依赖**，靠"示例库恰好是 RC"上线必踩 |
| 3.23 | 在线 DDL | 8.0 `ALGORITHM=INSTANT` 加列 | 11+ 加列带默认值很快；加约束可 `NOT VALID` 后校验；索引可 `CONCURRENTLY` | 🟡 | 运维差异，写进运维手册；大表变更策略两库各一份 |
| 3.24 | 严格模式 | 需 `STRICT_ALL_TABLES`（否则**静默截断/补零**） | 天然严格 | 🔴 | **上线必检**：非严格模式下 MySQL 会悄悄写坏数据，且两库行为不一致 |
| 3.25 | 大表归档 / 分区 | 分区表（InnoDB） | 声明式分区 | 🟡 | 操作日志（A22/M21）会是最大表 → **本期不做分区**，靠时间范围 + 索引，归档用应用层任务（两库同构） |

## 4. 开销量化（三档）

| 档 | 内容 | 一次性投入 | 每功能增量 | 占比估计 |
| --- | --- | --- | --- | --- |
| **零成本** | CRUD、条件查询、分页、逻辑删除、乐观锁、事务、唯一索引（规范化列方案） | 0 | ~0 | **约 85%~90% 的 SQL** |
| **小成本** | Upsert 分支、`DELETE…LIMIT` 改写、`NULLS LAST` 规避、时间取值、生成列/函数索引 | **约 2~3 人日**（建方言收敛层 + 约定） | 每处 **0.5~2 h** | 约 **10%~15%** |
| **大成本** | 全文检索、JSON 内部查询、部分索引直用、存储过程/触发器、跨库 JOIN | **5~10 人日**且需长期双维护 | — | **建议直接不做**（已在 §3 逐条给出替代方案） |

**推测口径（供你校准，可替换真实数字）**：假设管理面 **12 张表**、**60~90 条 Mapper 语句**：

- 需要方言分支的语句：**约 8~14 条**（upsert 3~4、TTL 清理 2~3、可空排序 2~4、索引/DDL 3）；
- 迁移脚本：`common` 同构部分 + 两套方言差异部分 → **每张表约 2 份 DDL**（12 张表 ≈ 24 个脚本，差异集中在 3~5 张表）；
- 测试：**Testcontainers 双库矩阵**（`mysql:8.0` + `postgres:16`）→ 集成测试耗时**约 ×2**（可只在主分支跑双库、PR 跑单库以省钱）；
- 运维：备份 / 监控 / 调优 / 升级文档**各一份**；
- **合计**：一次性 **约 8~12 人日**；此后每功能 **+5%~10%** 工作量。

> **一句话结论**：**"双支持"的成本不在写代码，而在"纪律"** —— 只要守住 §6 的禁止清单与规范化列方案，绝大部分 SQL 天然同构；反之，随便用一句 `ON DUPLICATE KEY` 就会把成本推到大成本档。

## 5. 三条落地路线（不代你拍板）

| 路线 | 做法 | 成本 | 风险 |
| --- | --- | --- | --- |
| **A · 单库优先** | 先只写 MySQL，**只保证语法不排斥 PG** | 最低 | 后期真要上 PG 时暴露方言债，返工集中爆发 |
| **B · 双库同级** ⭐ | 同构 DDL 语义 + **方言收敛层** + **CI 双库矩阵** | 中（≈8~12 人日） | 需要团队守纪律（靠 CI 卡口） |
| **C · 抽象方言层** | 自研 SQL 构建器 / 双份 Mapper | 高 | 过度设计，除非有强诉求 |
| **D · 只支持一个** | 写死 PG **或** MySQL | 最低 | 客户私有化若指定另一个库 → 返工（评审时需明确写入"不支持"） |

### 5.1 推荐：B + 三条硬机制

1. **MyBatis `databaseId` 分支**（最省事的内建机制）：配置 `VendorDatabaseIdProvider`（`MySQL` / `PostgreSQL`），同一 Mapper 里写 `<select id="x" databaseId="mysql">` 与 `databaseId="postgresql"` 两份 → **方言差异被限制在 XML 局部，Java 代码零分支**；
2. **方言收敛层**：最多 3~5 个方法（`upsert`、`batchInsert`、`limitOffset`（交给分页插件）、`deleteLimit`、`now`）→ 不让方言散落；
3. **CI 卡口**：脚本 grep Mapper XML，命中禁止清单关键字（`ON DUPLICATE KEY`、`GROUP_CONCAT`、`DATE_FORMAT`、`ILIKE`、`JSON_EXTRACT`、`->>`、`NULLS LAST`、`REPLACE INTO`、`INSERT IGNORE`…）即**构建失败**。

### 5.2 MyBatis-Plus 的免费部分（不用自己实现）

- **分页方言自动适配**：`PaginationInnerInterceptor`（传 `null` 或按 `DbType` 自动探测）；
- **逻辑删除**（`@TableLogic`）、**乐观锁**（`OptimisticLockerInnerInterceptor`）、**主键策略**（`IdType.ASSIGN_ID` 雪花）—— 都与方言无关；
- ⚠️ 但 **`IdType.AUTO` 依赖自增语义**，跨库行为（回填、间隙）不同 → 建议统一用 `ASSIGN_ID`。

### 5.3 例子：一个 Upsert 的两种写法（收敛到一处）

```xml
<!-- 同一个 statement id，按 databaseId 分流；Java 侧无感 -->
<insert id="upsertImportTool" databaseId="mysql">
  INSERT INTO import_tool (import_id, tool_key, payload, updated_at)
  VALUES (#{importId}, #{toolKey}, #{payload}, #{updatedAt})
  ON DUPLICATE KEY UPDATE payload = VALUES(payload), updated_at = VALUES(updated_at)
</insert>

<insert id="upsertImportTool" databaseId="postgresql">
  INSERT INTO import_tool (import_id, tool_key, payload, updated_at)
  VALUES (#{importId}, #{toolKey}, #{payload}, #{updatedAt})
  ON CONFLICT (import_id, tool_key)
  DO UPDATE SET payload = EXCLUDED.payload, updated_at = EXCLUDED.updated_at
</insert>
```

> 注意语义差异：MySQL 的 `ON DUPLICATE KEY` 命中**任意**唯一键（含主键），PG 必须**指定冲突目标**；MySQL 该语句还会消耗自增值。→ 这也是建议 `ASSIGN_ID` 的原因之一。

## 6. 本项目最可能踩的 6 个坑（含同构解法）

### 6.1 坑 1：名称唯一 + 大小写/尾空格/重音（对应管理面 `409`）

- **现象**：`"Weather"` 与 `"weather"` 在 MySQL 默认 collation 下**冲突**（回 `409`），在 PG 默认下**不冲突**（能建两个）→ 同一份服务/标签名规则，两库行为相反；
- **同构解法（推荐）**：新增 **`name_norm`** 列（应用层写入 `name` 的规范化形式：小写 + 去首尾空格 + Unicode NFKC），**唯一索引建在 `name_norm` 上** → 两库都用二进制/大小写敏感比较，行为完全一致；
- **附带好处**：搜索也统一查 `name_norm`（解决 §3.12 的 `LIKE` 大小写差异）；**不再依赖任何 collation**。

### 6.2 坑 2：软删除后重建同名（对应 §3.8）

- **同构解法**：`UNIQUE(name_norm, deleted_seq)`，`deleted_seq BIGINT NOT NULL DEFAULT 0`；删除时置为 `id`（或 `deleted_at` 的 epoch 毫秒）→ 可反复删建同名，两库一致；
- **禁用**：PG 的 `WHERE deleted_at IS NULL` 部分索引（MySQL 无对应，用了就锁死 PG）。

### 6.3 坑 3：TTL 清理（导入会话 30 分钟、会话存储）

- **同构写法**：`SELECT id FROM t WHERE expire_at < ? LIMIT 500` → `DELETE FROM t WHERE id IN (…)`；
- **禁用**：MySQL 的 `DELETE … LIMIT`；
- **更优**：**会话存储优先 Redis**（M12 三选一），DB 只做兜底 → 从根上少一类差异。

### 6.4 坑 4：时间与时区

- 统一：**应用层 `Instant.now()`**，列类型 MySQL `DATETIME(3)` / PG `timestamptz`，JDBC 参数统一 `OffsetDateTime`/`Instant`；
- **禁用**：`NOW()` / `CURRENT_TIMESTAMP` 作为业务时间来源、`ON UPDATE CURRENT_TIMESTAMP`（MySQL 专属）；
- MySQL 连接串必须带 `serverTimezone=UTC`（或 JDBC 4.2 的 `connectionTimeZone=UTC&forceConnectionTimeZoneToSession=true`）——**否则同一行数据两库读出来不一样**。

### 6.5 坑 5：MySQL 非严格模式静默写坏数据

- 上线检查：`SELECT @@sql_mode` 必须含 `STRICT_ALL_TABLES`（建议 `STRICT_TRANS_TABLES,NO_ENGINE_SUBSTITUTION,ONLY_FULL_GROUP_BY`）；
- 建议把它写进**连接初始化 SQL**（`spring.datasource.hikari.connection-init-sql`），而不是只依赖运维。

### 6.6 坑 6：操作日志表（A22/M21）的检索与体量

- 查询形态：**时间范围 + 对象维度 + 分页** → 两库同构 ✅；
- 排序若含可空列 → 用 `NOT NULL DEFAULT` 规避 `NULLS LAST`（§3.13）；
- **本期不做分区**；归档交给应用层任务（两库同构），避免 MySQL 分区表 vs PG 声明式分区两套运维。

## 8. 禁止清单（违反即拒 PR）

| 类别 | 禁用 | 替代 |
| --- | --- | --- |
| Upsert | `ON DUPLICATE KEY UPDATE`、`ON CONFLICT` 直接混用 | `databaseId` 双写（§5.3） |
| 插入 | `REPLACE INTO`、`INSERT IGNORE`、`INSERT … RETURNING` | 普通 `INSERT` + 显式判重 |
| 删除 | `DELETE … LIMIT` | `SELECT id … LIMIT` + `DELETE … IN` |
| 排序 | `NULLS FIRST/LAST` | 列 `NOT NULL DEFAULT`；或 `ORDER BY (col IS NULL), col` |
| 字符串 | `GROUP_CONCAT`、`string_agg`、`DATE_FORMAT`、`to_char` | 应用层格式化 / 聚合 |
| 大小写 | `ILIKE`、依赖默认 collation | `name_norm` 规范化列 |
| JSON | `JSON_EXTRACT`、`->>`、`@>`、JSON 内字段查询与索引 | 整块存取 + 应用层反序列化 |
| 索引 | PG 部分索引（`WHERE`）、依赖字符串默认 collation 的真正唯一 | `deleted_seq` 方案 + `name_norm`；**唯一列显式 `utf8mb4_0900_bin`（✅ B6）**；**"条件性唯一"有意用 NULL（✅ B7，见 DB 稿 C13a）** |
| 主键 | 依赖 `AUTO_INCREMENT`/`serial` 语义、`IdType.AUTO` | `IdType.ASSIGN_ID`（雪花）或 ULID |
| 时间 | `NOW()` 作为业务时间、`ON UPDATE CURRENT_TIMESTAMP` | 应用层 `Instant` |
| 隔离 | 依赖默认隔离级别 | **显式 RC（✅ B8 已定案）** + CI 断言 |
| 标识符 | 反引号 / 双引号包裹、保留字当列名 | 全小写下划线、非保留字 |
| DDL | `TEXT` 建唯一索引、`utf8`（非 `utf8mb4`） | `VARCHAR(≤200)`；`utf8mb4` + 显式 collation |
